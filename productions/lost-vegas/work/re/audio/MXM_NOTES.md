# Lost Vegas — audio format notes (MXM + procedural softsynth)

Reverse-engineering notes for the soundtrack of **"Lost Vegas"** by *threestate*
(Direct3D7 64k intro, Ambience 2000, March 2000). Binary analysed:
`work-lv/unpacked/3s-vegas-u.exe` (image base `0x400000`). Module blob:
`work-lv/extracted/vegas.mxm` (`0x5007` = 20487 bytes, the song data only — samples
are synthesized at runtime and appended after it).

The audio is **MXMPlay** (Niklas Beisert / "pascal"), a compact XM-repacker, driven
here by a bespoke **software (DirectSound) GUS-emulating mixer** rather than a real
GUS. Instrument samples are **not stored**; they are regenerated by a cosine-additive
softsynth at load time (the "distance decimating the sound" credit). A faithful `.xm`
therefore = the MXM song structure + PCM regenerated from the synth.

Format reference: `MXMPLAY.DOC` / `MXMPLAY.ASM` (github jarnoh/supermax), cross-checked
byte-for-byte against `vegas.mxm` and the exe's mixer.

---

## 1. Runtime pipeline (in the exe)

- `FUN_0040133c` (@0x40133c): allocates 1 MB, copies `0x5007` song bytes from
  `&DAT_00413000` (== `vegas.mxm`) into it, then calls the synth to **append** the
  generated PCM at `buf+0x5007`.
- `FUN_0040123d` (@0x40123d): synth driver → signed 8-bit PCM (see §3).
- `FUN_004114f1` (@0x4114f1): sets up DirectSound and starts the mixer thread
  `LAB_00411631`.
- Player/mixer (all EBP-relative on one big state struct):
  - `FUN_00410dc0` — per-tick player (reads pattern rows, envelopes, computes pitch).
  - `FUN_00410488` — note trigger (maps note→sample, sets voice fields).
  - `FUN_00410000` — the mixer (software GUS: 32 voices, linear interpolation,
    16.16-ish phase accumulator, forward/ping-pong looping).

## 2. MXM file format (as used by Lost Vegas)

All multi-byte values little-endian. Header offsets are **decimal**.

### 2.1 Header (`mxmheader`, 1872 = 0x750 bytes)

| off | size | field | vegas.mxm value |
|----:|-----:|-------|-----------------|
| 0   | 4    | signature `"MXM\0"` | `4D 58 4D 00` |
| 4   | 4    | `nOrders` (song length) | 25 |
| 8   | 4    | `ordLoopStart` (restart) | 0 |
| 12  | 4    | `nChannels` | 10 |
| 16  | 4    | `nPatterns` | 14 |
| 20  | 4    | `nInstruments` | 17 |
| 24  | 1    | `iniTempo` (ticks/row speed) | 6 |
| 25  | 1    | `iniBPM` | 125 |
| 26  | 2    | `options` (bit0=linear freq, bit1=?, bit2=samples delta-encoded) | `0x0001` |
| 28  | 4    | `sampStart` (offset of appended PCM) | `0x5007` |
| 32  | 4    | `sampMem8` (bytes of 8-bit sample data) | 29424 |
| 36  | 4    | `sampMem16` (16-bit sample bytes) | 0 |
| 40  | 4    | `pitchMin` | `0xffffb800` |
| 44  | 4    | `pitchMax` | `0x00006000` |
| 48  | 32   | `panPos[32]` (per-channel default pan, 0x80=center) | all 0x80 |
| 80  | 256  | `orderTable[256]` (pattern indices; `nOrders` used) | 10,9,7,7,6,… |
| 336 | 512  | `instrTable[128]` (dword file offsets of instruments) | 17 used |
| 848 | 1024 | `patternTable[256]` (dword file offsets of patterns) | 14 used |

`options` bit0 = **linear frequency table** (→ XM flags bit0). bit2 would mark
sample data as delta-encoded; **it is 0 here**, so the synth PCM is raw (not delta).

### 2.2 Patterns (S3M-style packing)

Each pattern (pointed to by `patternTable`):
```
dword numRows
then, per row: a sequence of channel events, terminated by a 0 flag byte.
```
Event = **flag byte** then optional fields:
- bits 0-4 (`0x1F`) = channel index
- bit 5 (`0x20`)   = note byte + instrument byte follow
- bit 6 (`0x40`)   = volume-column byte follows
- bit 7 (`0x80`)   = effect byte + parameter byte follow

`note`: 0 = none, 1..96 = C-0..B-7, 97 = key-off. `instrument`: 1-based, 0 = none.
`volume`: standard XM volume-column byte (0 = none). Empty channels for a row are
simply omitted; a `0x00` flag ends the row.

### 2.3 Effect command numbering

MXM stores a **linearized** command (`proccmdtab` index), not the XM nibble:
- **0..33** map 1:1 to XM effect numbers `0x00..0x21`
  (`0`=arp, `1`=porta↑, `2`=porta↓, `3`=tone-porta, `4`=vibrato, `5`,`6`, `7`=tremolo,
   `8`=pan, `9`=offset, `A`=vol-slide, `B`=jump, `C`=set-vol, `D`=break, `F`=speed,
   `G/H`=global-vol, `K`=key-off, `P`=pan-slide, `R`=retrig, `X`=extra-fine porta, …).
- **36..51** are the expanded `Exy` sub-commands: command `36+sub` → XM effect `0x0E`,
  param `(sub<<4)|(dat&0x0F)` (e.g. 37=E1 fine-porta-up, 49=ED note-delay, 50=EE
  pattern-delay).
- Custom `sync` (28) and a couple of `0`-slots have no XM equivalent and are dropped.

Volume-column bytes are already in XM encoding, copied through unchanged.

### 2.4 Instruments (fixed 272 = 0x110 bytes each)

```
+0   dword insNSamples            (1 for every Lost Vegas instrument)
+4   byte  insSamples[96]         note→sample keymap (all 0 here)
+100 word  insVolFade             fadeout speed
+102 byte  insVibType/Sweep/Depth/Rate   auto-vibrato (all 0 here)
+106 byte  insVNum/VSustain/VLoopS/VLoopE
+110 word  insVEnv[12*2]          volume envelope: 12 × (spanTicks, value)
+158 byte  insPNum/PSustain/PLoopS/PLoopE
+162 word  insPEnv[12*2]          panning envelope
+210 byte  pad[46]
+256 …     one 16-byte sample header (see below)
```

Envelope points are **(segment-length-in-ticks, value)** pairs, not absolute frames.
`VNum` is the **last-point index** (point count = VNum+1). Lost Vegas envelopes are
near-flat (sustain at 64, fadeout on key-off).

### 2.5 Sample header (Vegas repacked, 16 bytes, at instrument+256)

This is **not** the GUS-original `sample` struct; the software-mixer build repacked
it. Confirmed from `FUN_00410488`:

```
+0  dword loopStart      (bytes, relative to sample start)
+4  dword end            (= sample length in bytes)
+8  byte  mode           GUS voice control: bit3(0x08)=loop, bit4(0x10)=bidirectional
+9  byte  defVol         0..64
+10 byte  defPan         0..255
+11 word  normNote       signed relative pitch, **256 units / semitone**
+13 word  sampleIndex    selects the sample-base pointer
+15 byte  pad
```

`mode`: `0x00` = one-shot, `0x08` = forward loop, `0x18` = ping-pong loop.

## 3. The procedural softsynth

Ported in `work-lv/audio/synth.mjs` from the x86 disassembly (the Ghidra C mangled the
`+0x60` param stride and the float/double loads — the asm is authoritative).

Constants from `.rdata`: `FREQ0 = π/256` (single, `0x412080`), `FREQ1 = π/64` (double,
`0x412078`), `SCALE = 1/256` (double, `0x412088`), and 8 harmonic coefficients at
`0x41a284`: `[0.124996, -0.25, 0.249061, -0.234831, 0.176782, -0.085736, 0.021643,
-0.001933]`. Parameter bitstream at `0x418008` (dumped to `audio/synth_params.bin`,
8828 bytes; first dword = `1183` steps).

Float32 work buffer (indices from base `&DAT_00421668`):
`WAVE[0..0x200)`, `WIN[0x200..0xa00)` (32 rows × 64), `ACC[0xa00..0xc00)` (overlap-add
delay line), `PARAM[0xc00..0xe00)` (16 steps × 32 partials).

- **`FUN_00401000`** builds the tables:
  `WAVE[k] = (±) Σ_{j=0..7} coef[j]·cos((j·k)·π/256)`, negated when `k&0x40`;
  `WIN[m][c] = cos((n0 + c·step)·π/64)` with `n0 = -16-32m`, `step = 1+2m`.
- **`FUN_004010c0`** unpacks, per 16-step block, three 32-bit masks (`m1,m2,m3`) then a
  packed bitstream. Each partial's mask combination selects `(nbits, shift)`:
  `m1&m2→(4,4)`, `m1&m3→(4,3)`, `m2&m3→(4,2)`, `m1→(2,2)`, `m2→(2,1)`, `m3→(2,0)`,
  none → zero-fill. Value =
  `(((sext8(byte) << nbits) & ~0x7f) | 0x80) << shift`, then `× 1/256`; the byte is
  MSB-first, `8/nbits` samples per byte (never crosses a byte, since nbits ∈ {2,4}).
- **`FUN_004011e9`** synthesises one step: for each of 64 positions `t`,
  `acc = Σ_i param[i]·WIN[i][t]`, then `ACC[t+64k] += acc·WAVE[t+64k]` for k=0..7.
- **`FUN_0040123d`** runs `count`(=1183) steps; each step reads 32 samples off the top
  of `ACC` (descending, `round`+clamp to signed 8-bit), shifts `ACC` up by 32 and
  clears the bottom 32. The first `0x1e0` (480 = 15 steps) priming bytes are dropped.

Output: one continuous **signed 8-bit** stream (37376 bytes; only the first ~29420 are
referenced by instruments).

`synth.mjs` keeps the synthesis core in float and exposes the quantizer and the
sample rate as options (`{bits, oversample}`) for the remaster build; the defaults
reproduce the above byte-for-byte, and `synthesizeFloat()` returns the unquantized
stream. See §8.

## 4. MXM → XM mapping (`mxm2xm.mjs`)

- Header → XM 1.04: linear flag, speed=6, BPM=125, 25 orders, 14 patterns, 10 channels,
  17 instruments; order/pattern tables copied directly.
- Patterns → XM packed patterns (note/instrument/volume copied; effects via §2.3).
- **Samples**: each instrument is synthesized as its **own run** of 32-sample steps.
  Every run starts with **15 steps (0x1e0 = 480 bytes) of filter warm-up** that is *not*
  part of the sample, and runs are aligned to the 32-sample step grid. The driver drops
  only the *first* run's warm-up globally (`puVar2 + 0x1e0`), so all later warm-ups stay
  embedded in the stream. Offsets are therefore:
  ```
  off[0]   = 0
  off[i+1] = ceil32(off[i] + len[i] + 480)
  ```
  Verified exact for all 17 instruments against the oracle XM (§7). This is why
  Σ len = 29420 < the 37376-byte stream: the ~8 KB difference is the embedded warm-ups.
  Each instrument's sample = `pcm[off : off+end]`, delta-encoded for XM.
  *(An earlier revision assumed consecutive packing with no warm-up gaps — correct
  lengths but every instrument after #0 read the wrong bytes. See §7.)*
  - loop type from `mode` (0x08→fwd, 0x18→ping-pong); loopStart = `loopStart`,
    loopLength = `end - loopStart`.
  - `defVol`→volume, `defPan`→panning.
  - **relativeNote / finetune** from `normNote`: `rel = round(normNote/256)`, then
    `finetune = round((normNote − rel·256)/2)` (XM finetune is 128 units/semitone, half
    of MXM's 256). Both formats anchor note 49 (C-4) at rel/norm 0.
    **The (rel, finetune) split is ambiguous** — only `rel + finetune/128` is the actual
    pitch, so `(-31, +13)` and `(-30, -115)` are the same note. When the nearest `rel`
    falls outside XM's legal `[-48, 71]`, **borrow the remainder into finetune** rather
    than clamping `rel` (clamping detunes by a whole semitone). `ins5` is exactly this
    case: `normNote = -12544 = -49.0` semitones → emitted as `rel = -48,
    finetune = -128`, which is bit-identical to the oracle's encoding.
- Volume envelope converted (span→absolute frames), sustain + fadeout enabled; pan
  envelope disabled (all instruments have PNum 0); auto-vibrato all zero.

## 5. Ground truth: the oracle XM

`reference/oracle/dst_vega.xm` — distance's own release of the soundtrack
("deluxe decimator 3", FastTracker v2.00, 47016 bytes), published the same month as the
intro. It is the decisive reference for validating the reconstruction.

**Confirmed identical** between oracle and our reconstruction:
- 10 channels, 14 patterns, 17 instruments, speed 6, BPM 125, linear frequency.
- All 17 sample **lengths**: 356, 812, 698, 534, 938, 310, 678, 650, 560, 5792, 3560,
  2828, 2520, 3214, 520, 3696, 1754.
- All 17 **effective pitches** (`rel + finetune/128`), exactly.
- Sample **content**: mean NCC **0.985**, worst 0.962 (see §7).

**Deliberate difference — the intro plays an EDIT of the released tune:**

| | orders | order table |
|---|---:|---|
| oracle | 27 | `10,9,`**`9,8,`**`7,7,6,6,6,6,8,8,9,9,6,6,6,6,1,0,8,8,11,5,4,3,2` |
| intro (`vegas.mxm`) | 25 | `10,9,7,7,6,6,6,6,8,8,9,9,6,6,6,6,1,0,8,8,11,5,4,3,2` |

The intro drops the oracle's orders at index 2 and 3 (patterns 9 and 8) — ~11.3 s of
music. **The intro's 25-order table is authoritative for the restoration.** This fully
explains the duration difference and the −11.3 s offset the oracle shows against the
reference capture; there is **no tempo drift and no missing jump** (see §7).

The oracle also gives `ins14` a loop (start 100, length 120) where the intro's MXM has
`mode = 0x00` (one-shot). The MXM is authoritative for the intro, so we keep one-shot.

## 6. Validation & open questions

`validate.mjs` loads each build with the user's `../work/xm.js`, checks it against the
oracle's sample table, renders 30 s → `audio/<name>_preview.wav`, and cross-correlates
a full-length render against `reference/ref_audio.raw`. `vegas.xm`: loads clean,
**no unsupported effects**, 10 ch / 14 pat / 17 ins / 25 orders, non-silent (peak 0.64,
RMS 0.10, 89 % nonzero). Full table for both builds in §8.5.
Helpers live in `audio/dsp.mjs`; `audio/oversample_test.mjs` is the §8.2 experiment.

**Open items:**
1. **Synth bit-exactness.** JS uses double + `Math.fround` + `Math.round`; the x87
   original uses 80-bit intermediates and round-half-to-even. This is the most likely
   cause of the residual ~1.5 % sample difference vs the oracle (§7). Audibly
   negligible.
2. Effect fidelity relies on the `proccmdtab` index table matching XM numbering (it
   does for 0..33 and the E-group); rare custom `sync` commands are dropped.
3. The oracle's `ins14` loop is not applied (see §5) — intentional.

## 7. Debugging the synth against the oracle (what was actually wrong)

Rendering the first reconstruction against `reference/ref_audio.raw` gave raw-waveform
NCC ≈ 0.12–0.17 (noise) while the oracle gave ≈ 0.33–0.58 — right notes, wrong sound.
The decisive experiment was to extract the oracle's 17 sample PCMs (standard XM,
un-delta'd) and slide each one over the synth's 37376-byte output stream:

**Every oracle sample matched the synth output at NCC 0.96–0.998 — but at offsets that
were not the ones being used.** So the synth port (`FUN_00401000` / `004010c0` /
`004011e9` / `0040123d`) was correct all along; the bug was entirely in **where each
instrument's sample starts in the stream** (`mxm2xm.mjs`).

Best-match offsets recovered by correlation: `0, 864, 2176, 3360, 4384, 5824, 6624,
7808, 8960, 10016, 16288, 20352, 23680, 26688, 30400, 31424, 35616`. These are all
multiples of 32, and the gap between each sample's end and the next sample's start is
consistently 480–508 bytes — revealing the rule in §4:
`off[i+1] = ceil32(off[i] + len[i] + 480)`, i.e. a discarded 15-step filter warm-up per
instrument, step-grid aligned. The rule reproduces all 17 offsets exactly.

Two fixes were applied: the offset rule above, and the relativeNote/finetune borrow for
`ins5` (§4). Results after the fix:

| metric | before | after | oracle |
|---|---:|---:|---:|
| sample content NCC vs oracle (mean) | — | **0.985** | 1.0 |
| raw-waveform NCC vs reference capture | 0.12–0.17 | **0.597** | 0.327 |
| energy-envelope NCC vs reference | — | **0.917** | 0.914 |

The reconstruction now matches the reference capture **better than the composer's own
released XM**, because ours carries the intro's 25-order edit and locks at a flat
**+0.23 s** lag across the whole piece, whereas the oracle needs −11.3 s and drifts
within windows. The lag being constant start-to-finish (+0.21 s … +0.23 s) is the
direct measurement confirming **there is no tempo drift** — speed 6 / BPM 125 is right.

### Tick-rate formula (documented while chasing the drift hypothesis)

Ruled out as a defect, but worth recording. The audio callback `FUN_00410289` keeps an
8.8 fixed-point sample accumulator and advances the player one tick at a time:
```
mov eax, 0x541D3400        ; 1411827200
mov ebx, [ebp+0x25]        ; BPM (from hdIniBPM)
imul ebx, ebx, 0x32        ; BPM * 50
idiv ebx                   ; eax = increment, in 8.8 fixed point
add [ebp+0x4b7f], eax      ; tick accumulator
...
shr ecx, 8                 ; whole samples to render this slice
```
So **samples-per-tick = 1411827200 / (BPM · 50 · 256) = 5514950 / (BPM · 50)**. At
BPM 125 that is 882.392 samples — versus the standard `rate·2.5/BPM` = 882.0 at
44100 Hz, i.e. only **+0.04 %**. The implied reference rate is 44119.6 Hz. Truncation
is to whole samples per *slice*, with the fractional remainder carried in the
accumulator, so it does not accumulate error. This is nowhere near the ~4 % that the
duration comparison suggested, which is what first indicated the difference had to be
structural (the dropped orders) rather than a timing bug.

## 8. The remaster layer (`vegas_remaster.xm`) — strictly additive

`vegas.xm` is the authentic artefact and is **byte-frozen** (sha256
`1c36963a…`). `vegas_remaster.xm` is an *additive* quality build produced by the
same pipeline with two options raised. Both come out of one `node audio/mxm2xm.mjs`
run (the `BUILDS` table at the bottom of the file).

| | vegas.xm | vegas_remaster.xm |
|---|---|---|
| sample words | signed 8-bit | signed **16-bit** (XM sample type bit 4) |
| generation rate | 1x | **2x**, relativeNote +12 |
| sample data | 29 420 B | 117 680 B |
| file size | 47 018 B | 135 278 B |

### 8.1 16-bit

`synth.mjs` always synthesised in float and threw the rest away at the final
`round`+clamp to int8, purely because the 2000-era format stored 8 bits.
`synthesize(stream, {bits:16})` emits `round(v*256)` clamped to `[-32768, 32767]`
instead. The clip ceiling stays put — +127.996 vs the original's +127, within one
8-bit LSB — so the original's clipping *character* is preserved (and it does clip:
433 of 37 376 samples exceed int8 range; the float stream peaks at −158.7/+154.2).
Only the quantization floor moves, by **−44.9 dB measured** on a 40 s render.

### 8.2 Oversampling — the experiment, and why the answer is "yes"

At OS the synth's every cosine phase increment is divided by OS and every buffer
(WAVE, WIN, ACC delay line, step size, the 15-step warm-up) multiplied by OS, so
the same *continuous* functions are sampled OS times more finely. `audio/oversample_test.mjs`
runs the decisive test against the oracle's real samples:

| | mean NCC vs oracle | worst |
|---|---:|---:|
| 1x float (baseline) | 0.9853 | 0.9619 |
| 1x int8 (shipped authentic) | 0.9853 | 0.9615 |
| 1x int16 | 0.9854 | 0.9618 |
| 2x → naive decimation (control) | 0.9853 | 0.9619 |
| **2x → band-limited decimation (verdict)** | **0.9851** | 0.9618 |

**Verdict: the aliasing is NOT load-bearing — adopt.** Band-limiting away
everything that folded down at 1x costs **0.0002 NCC**, i.e. nothing. The folded
energy measures **−34.9 dB** relative to the in-band signal, which is what the
structure predicts: WAVE is 8 low harmonics (≤ 7/512 cyc/sample) times a pointwise
square wave of period 128, and the square's harmonics above Nyquist_1x are the
m ≥ 32 terms, whose power sums to ~0.3 % of the total.

Two traps this test walked into and out of, both worth keeping:

1. **The control is mandatory.** The first run reported 0.8646 for *both* the
   naive and the band-limited decimation — which would have read as a resounding
   "the aliasing is everything". It was a **half-sample phase error**: each
   synthesis step reads its output off the *top* of the delay line **descending**
   (`ACC[accLen-1-j]`), so at OS the 1x grid lands on sub-phase `OS-1`, not 0.
   Decimating on sub-phase 0 shifts everything by half a sample, which no integer
   lag search can undo. With the phase fixed, `max |1x − naive(2x)| = 0` exactly —
   the 2x generator is a bit-exact super-sampling — and only then is the
   band-limited number interpretable. **A verdict test without a control that
   pins to a known answer is not a test.**
2. The oracle's samples are themselves 8-bit and 1x, so they *contain* the folded
   content. That is precisely what makes them the right ground truth here.

### 8.3 What oversampling actually changes (it is not the samples)

Rendering all four combinations through `work/xm.js` for 40 s and differencing
against the authentic build separates the two effects cleanly:

| build | NCC vs authentic | difference |
|---|---:|---:|
| 16-bit 1x | 0.999984 | −44.9 dB |
| 8-bit 2x | 0.969710 | −12.2 dB |
| 16-bit 2x (shipped) | 0.969714 | −12.2 dB |

So the audible delta is **dominated by oversampling, and it happens in the
player, not in the samples**. `work/xm.js` mixes with linear interpolation; most
voices sit at relativeNote −48…+9, i.e. they step through the sample well below
1.0, and linear interpolation on a sparse grid generates spurious HF imaging.
Doubling the source grid roughly quarters that error, which is why the 30 s render's
95 % spectral rolloff drops 8836 → 7277 Hz and the centroid 2240 → 2146 Hz. That
removed content is **replayer distortion, not instrument** — the samples themselves
are confirmed identical to the oracle (§8.2). Worth knowing when A/B-ing: the
remaster is measurably *smoother*, and someone attached to tracker grit may hear
that as a change rather than an improvement. The 1x/16-bit variant is one line in
the `BUILDS` table if that is ever preferred.

### 8.4 Pitch bookkeeping

Storing OS× as many frames means the sample must sound `12*log2(OS)` semitones
higher. `mxm2xm.mjs` adds `relShift*256` to `normNote` *before* the rel/finetune
split, so the split's remainder (and therefore `finetune`) is unchanged and the
period-table index shifts by exactly `12*16 = 192` — an exact octave in XM's
linear table (period −768 → frequency ×2). Loop points and lengths scale by OS.

This also **fixes `ins5` outright**: its −49.0 semitones no longer needs the
`rel=-48, finetune=-128` borrow against XM's relativeNote floor, becoming a clean
`rel=-37, finetune=0`. relativeNote range goes from `[-48, 9]` to `[-37, 21]`,
still well inside xm.js's `[-48, 71]` clamp (4x would also fit, at 253 KB).

### 8.5 Validation of the shipped remaster

`node audio/validate.mjs` (both builds, `work/xm.js` as the replayer):

| | vegas.xm | vegas_remaster.xm |
|---|---:|---:|
| loads, unsupported effects | 0 | 0 |
| structure | 10 ch / 14 pat / 17 ins / 25 ord / 6 / 125 / linear | identical |
| sample lengths vs oracle | 17/17 exact | 17/17 exact (×2) |
| effective pitches vs oracle | 17/17 exact | 17/17 exact (−12 st) |
| peak / RMS (30 s @48k) | 0.638 / 0.096 | 0.669 / 0.097 |
| crest | 16.4 dB | 16.7 dB |
| capture NCC (per-window mean) | 0.5606 | 0.5556 |
| capture NCC (pooled, single lag) | 0.4228 | 0.4195 |
| energy-envelope NCC | 0.9466 | 0.9473 |
| lag | −0.223 s, spread 0.010 s | −0.223 s, spread 0.028 s |

xm.js also decodes the shipped 16-bit delta-encoded data back to the generator's
output **bit-exactly for all 17 instruments** (round-trip check).

The remaster tracks the capture within ±1 % of the authentic build on every
pooling — marginally below on raw waveform, marginally above on envelope, both far
inside the window-to-window spread (0.35…0.68). The tiny raw-waveform deficit is
the expected sign: the capture carries the original mixer's own 8-bit linear-interpolation
artefacts, which the 1x build reproduces and the 2x build cleans up.

**Methodology note (constrained windows).** The capture figures are 10 s windows,
each re-aligned within ±1.5 s of a global lag that is itself found in a ±1.5 s
window. The constraint is not optional: the song repeats patterns every ~3.7 s, so
an unconstrained argmax false-locks onto a neighbouring bar — this has already
produced one wrong result on this project. Two independent checks that the harness
is sound: it recovers the oracle's documented **−11.3 s** offset (measured 11.297 s,
opposite sign convention) and its documented envelope NCC (0.928 vs 0.914), and it
puts the authentic build's lag flat at −0.22…−0.23 s across all 17 windows,
reconfirming **no tempo drift**. Its absolute raw-waveform number for `vegas.xm`

## 9. Visual sync — the graphics timeline interface

**The whole demo timeline is driven by music position, not wall clock.** The master
loop `FUN_0040f285` is a ladder of `while (quit==0 && pos < THRESHOLD)` blocks. `pos`
comes from `FUN_004051ef`, which reads the audio player's song position.

### 9.1 The 16-bit song position (`FUN_00410678`)

The audio callback `FUN_00410289` snapshots the live player state every buffer fill:
```
EBP+0x4ba0 = EBP+6     ; current ROW within the pattern      (dword)
EBP+0x4ba4 = EBP+0x12  ; current ORDER (order-table index)   (dword)
```
`FUN_00410678` returns the 16-bit value **`(order & 0xff) << 8 | (row & 0xff)`**.

So it is **NOT** a linear row/tick counter — it is `order:row` packed as two bytes.
`order` is the index into the order table (0..songLength-1, here 0..24); `row` is the
row within the current pattern (0..63). It advances **per row** (row bumps once every
`speed`=6 ticks; order bumps at pattern end / on Bxx/Dxx). At song start order=row=0 so
the raw value is 0.

### 9.2 What the timeline actually compares (`FUN_004051ef`)

```
raw = FUN_00410678()            ; (order<<8)|row
p   = (raw - 1) & 0xffff
if (p > 0x3000) p = 0           ; also maps the raw==0 start (0xffff) to 0
if (p > 0x1ff)  p = p + 0x200   ; hard-coded discontinuity once order >= 2
return p                        ; <- compared against the scene thresholds
```
The `+0x200` shim inserts a fixed gap once past order 1 — reproduce it exactly or the
later thresholds shift by 0x200.

Scene thresholds (from `FUN_0040f285`, in order):
`0x114, 0x200, 0x600, 0x800, 0xa00, 0xc00, 0xe00, 0x1200, 0x1400, 0x1600, 0x1a20`
(end clamp `0x3000`). A scene runs while `pos < threshold`; it changes at the threshold.

### 9.3 Reproduce from xm.js

The reconstructed `vegas.xm` keeps the MXM order/pattern numbering 1:1, so xm.js's live
`player.position` (order) and `player.row` map directly. `audio/sync.mjs` exports:
```js
import { musicPos, SCENE_THRESHOLDS } from './audio/sync.mjs';
const pos = musicPos(player);   // call once per frame; gate the scene ladder on it
```
`musicPos` = `(((position&0xff)<<8 | (row&0xff)) - 1) & 0xffff`, then the clamp/shim.
