# winebox — running the Win32 originals as their own test oracle

Planet Potion's strongest checks came from executing the original's own code and
reading its output (METHOD.md, "Run the original's own code instead of
reimplementing it"). The Haujobb productions are Win32/x86, and this is the
equivalent apparatus. **Spike completed 2026-08-20; the technique works.**

The shape is different from the Amiga case, and the difference matters. Almost
nothing here is a *pure* subsystem worth executing, because the assets are files
on disk rather than generated by code. The valuable target is the other half of
the technique: **the library calls are the output.** Every one of these
productions reaches OpenGL through the import table or `wglGetProcAddress`, so
recording that boundary yields the program's own draw stream — a per-frame
primitive list to diff a reimplementation against, offline, before a pixel is
rasterised.

Wine already *is* the recorder. `WINEDEBUG=+opengl` prints every call into
opengl32 with its arguments, in call order, before forwarding it. No stub to
hand-build, no hardware, no capture.

## What was measured

| | |
|---|---|
| host | Apple Silicon (aarch64), Docker Desktop 29.7.2 |
| container | `--platform linux/386` — **works**; `uname -m` = i686 |
| wine | 8.0 (Debian bookworm i386), runs under the emulation |
| GL | Mesa llvmpipe, software, no GPU |
| subject | `Genoaux.exe` from the pinned original |
| result | **156,286 GL calls with full arguments, 19 frames, in ~75 s** |
| reproducibility | two runs **byte-identical** after stripping thread ids |

The recorded profile independently confirms the static analysis: fixed-function
throughout, `glMultiTexCoord2fARB` in real use, display lists, matrix stack —
and no shader-era call of any kind.

## Two things that will waste an afternoon if you do not know them

**The setup dialog blocks everything.** The engine opens an MFC dialog (Run Demo
/ window / fullscreen) and waits. Headless, nothing presses it, the program
emits **zero** GL calls, and the run reads exactly like a rendering failure
rather than an un-pressed button. `record-gl.sh` drives it with `xdotool` and
logs the attempt, so an un-pressed dialog is visible in the output. This cost
one full probe run here.

**Frames are delimited by `glClear`/`glViewport`, not `wglSwapBuffers`** —
`+opengl` does not trace the swap, which lives in the gdi/winex11 path.

## Making time an input — SOLVED, with no patching at all

The first probe found the clock frozen: no audio device, `BASS_Init` fails, and
Genoaux's show clock is BASS byte-position ÷ 176.4, so the demo rendered the same
instant forever (19 frames, repeating **byte-identically** cycle to cycle — the
proof of determinism and the proof that time was not moving, at once).

The fix is one file. Give ALSA a **null device** and BASS opens, the stream runs,
and the clock advances:

```sh
printf 'pcm.!default { type null }\nctl.!default { type null }\n' > /etc/asound.conf
```

| `[mp3]` start offset | GL calls | frames |
|---|---|---|
| frozen (no audio device) | 156,286 | 19, repeating |
| 0 s | 833,807 | 1,117 |
| 100 s | 745,906 | 1,004 |

That second and third row are the result that matters. **`Script.txt`'s `[mp3]`
start offset — its third line, a position in seconds applied through
`BASS_ChannelSetPosition` — is a working time input.** Offset 0 and offset 100
produce substantially different traces, where without an audio device they were
byte-identical (0 differing lines): the seek was always real in the parser, it
just could not act on a stream that never opened.

So the oracle needs **no stub DLL and no binary patch**. Time is supplied through
the original's own configuration file, down the original's own seek path — which
is what METHOD.md's "make time an input" asks for, in its cheapest possible form.

**The stub is now built** — see `bassstub/` and `BASS_STUB_NOTES.md`. It replaces
`BASS.DLL` with 11 undecorated exports whose stdcall widths were measured from
Genoaux's own call sites, and additionally patches the main module's IAT entry for
`GetTickCount`, because pinning the BASS position alone does **not** freeze the
show. With both clocks pinned, two independent runs give **161,833 GL calls, 29
frames, byte-identical streams**. That upgrades the oracle from "sampled from a
moving show" to "addressed by position".

The `Script.txt` offset route below still works and needs no build, so it remains
the quick path; the stub is the exact one.

## The seek lands where the script says it does

"The traces differ" is not a result; the script's own part table predicts *how*
they should differ, and that is decidable. `Script.txt` declares two parts:

```
[part] Silhuets.hjb  144115      <- geometry-heavy scene, until 144.1 s
[part] Black.hjb     160000      <- 1105-byte scene + fullscreen End_Titles overlay
```

So a seek past 144 s should collapse the geometry and replace it with a
fullscreen quad. Measured:

| offset | display lists | draw ops | primitives | calls/frame | distinct frames |
|---|---|---|---|---|---|
| 0 s | 61,183 | 433,956 | 34 | 745.8 | 132 |
| 100 s | 53,191 | 377,379 | 114 | 742.2 | 117 |
| **150 s** | **1,195** | **8,955** | **870** | **415.5** | **12** |

Offset 100 is still inside part 1 and stays geometry-heavy. Offset 150 crosses
the 144.1 s boundary: display lists collapse **51×**, and immediate-mode
primitives rise as the overlay quads take over. That is the script's own part
table reproduced from the outside, so the seek is landing, not merely perturbing.

## The artifact: a per-frame draw stream

`parse-gl-trace.mjs` turns the log into one record per frame — the ordered ops
the engine submitted, the texture bound to each, and the matrix operations
around them:

```
frame 20  digest=dc334128f522  calls=69  lists=0
  ops: ["bind 14@TEXTURE0","prim QUADS:4:t14","bind 15@TEXTURE0","prim QUADS:4:t15", ...]
```

```sh
node tools/winebox/parse-gl-trace.mjs out/gl.log --out frames.jsonl
node tools/winebox/parse-gl-trace.mjs out/gl.log --frame 20     # one frame, pretty
node tools/winebox/parse-gl-trace.mjs out/gl.log --summary --min-frames 100
```

Exit codes: 0 consistent · 1 malformed, unbalanced, or below `--min-frames` ·
**77 no trace lines at all** (absent, not empty).

**Ordering is the check.** METHOD.md: the Nth call is the Nth result. Frames are
digested over their *ordered* op stream, never over a histogram of it — bucketing
by type and counting is the weak test that cannot separate two producers sharing
a value. Host pointers (`glTexImage2D`'s `pixels`) are dropped deliberately;
they vary run to run and would destroy comparability.

### Two bugs this tool had, both worth knowing

**It was blind to the entire show.** The first version digested only
`glBegin`/`glEnd` primitives and reported **2 distinct frames across 1,118** —
because this engine compiles geometry into **display lists** at load and then
draws by replaying them. 1,117 frames contained no `glBegin` at all. Whatever an
engine varies per frame is what the oracle must capture; here that is the matrix
stack, the bound texture, and which lists are called.

That failure is now its own assertion: a run of ≥10 frames yielding fewer than 3
distinct digests **exits 1**, so the property cannot quietly vanish again.
Verified by sabotage — forcing a constant digest gives
`FAIL: 438 frames but only 1 distinct digest(s)`, and restoring returns 0.

**`glActiveTextureARB`'s argument is `texture`, not `target`** (its sibling
`glMultiTexCoord2fARB` uses `target`). Reading the wrong one silently emitted
`bind 14@undefined` and dropped the multitexture unit from every record.

## Usage

```sh
docker build --platform linux/386 -t haujobb-winebox -f tools/winebox/Dockerfile.winebox tools/winebox
docker run --rm --platform linux/386 \
  -v "$PWD/productions/genoaux/work/unpacked/hjb_geno:/demo:ro" \
  -v "$PWD/tools/winebox:/work" \
  haujobb-winebox sh -c 'cp -r /demo /tmp/d && sh /work/record-gl.sh /tmp/d/Genoaux.exe 75 /work/out'
```

The image is ~1.6 GB and builds slowly (emulated i386 apt). Like `ppcbox.sh`,
anything that cannot run should exit **77 — absent** rather than pass silently.
